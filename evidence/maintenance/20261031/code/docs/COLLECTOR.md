# Автоматический журнал лаборатории

## Чтение сжатых журналов — 31 октября 2026

Сборщик, явный захват и просмотр инструментов поддерживают `.jsonl.zst`.
Если прежний `.jsonl` отсутствует, проверяется только его точный сосед
`.jsonl.zst`; поиск других файлов и переход по симлинкам запрещены.
Распаковка идёт во временный файл с ограничением размера. Номера строк,
смещения и контрольные суммы относятся к исходным распакованным байтам,
поэтому прежние записи и курсоры сохраняют смысл. Повреждённый архив,
изменённый сохранённый префикс или подмена источника останавливают его сбор.
Неизменившийся сжатый источник повторно не распаковывается.

Нужен Python 3.14+ со стандартным `compression.zstd` либо установленная
локальная команда `zstd` для более раннего Python. Ошибочные сессии теперь
сохраняют известные пробелы в общей сводке и не дают ложного healthy.
Это ремонт чтения источников; он не отменяет прежние ограничения захвата
инструментов, вложений и неизвестных форматов.

Код: `scripts/codex_rollout.py`; проверки: `tests/test_codex_rollout.py`.
Фактическая приёмка ремонта и состояние службы: `runs/maintenance-20261031/`.

Сборщик — локальный процесс Python под macOS launchd. Он не вызывает модели,
API или сеть и не расходует лимиты подписки. Чаты хранятся в файлах; чтение
архива сборщиком не загружает их в контекст исследовательской модели.
Реализация и приёмка: 8 сентября 2026 UTC / 7 сентября America/Los_Angeles.

## Область сбора

Все native-сессии с точным cwd этой лаборатории, два явно выбранных исторических
ID из `collector/config.json` и их потомки по native `thread_spawn_edges`.
Другие чаты Math Career OS и фабрики не входят. Обнаружение читает только
метаданные SQLite; источник каждого выбранного файла сверяется по ID и cwd.
Native `subagent.other` (в частности внутренний guardian проверки действий)
учитывается только как исключённая служебная сессия, без чтения её тела.
Переименование не создаёт новый чат. Новый ID означает отдельную сессию.
Смена пути проекта, вынос в worktree или перенос на другой компьютер требуют
обновления области; путь или родство не угадываются по похожему названию.

Основные чаты и субагенты считаются отдельно. У субагента `role=user` может
быть унаследованной историей или AI-поручением: эти записи не объявляются новыми
человеческими вкладами. Доступные nickname, role, agent_path и parent ID
сохраняются с источником. Техническая роль не подменяется придуманной задачей.
Поручения доступны там, где они присутствуют в видимых сообщениях или отдельно
проверенных tool bodies. Глобальный порядок архива — порядок фиксации;
порядок внутри чата — исходные строки и turn ID. Параллельные чаты не образуют
одного искусственного последовательного разговора.

## Что сохраняется и как читать полноту

Автоматически: распознанные пользовательские промпты, commentary и финалы AI;
их безопасные точные native-байты; время исходной записи и отдельное время
архивирования; наблюдаемые модель/effort; начало, завершение, прерывание хода,
доступные duration и TTFT; связи сессий и метаданные инструментов.

Исходные lifecycle-времена могут быть Unix seconds: сохраняются значение,
единица, точность и нормализованное UTC. Длительность — wall time хода,
включая инструменты и ожидание. TTFT из native-метрики и задержка до первой
видимой записи — разные поля. Скрытое время мышления и фактическая серверная
маршрутизация не восстанавливаются из этих данных. Отсутствующее — `UNKNOWN`,
текущий ход — `ONGOING`, прерванный — `INTERRUPTED`. Позднее завершение
дополняет уже сохранённый финал без дублирования сообщения.

`TEXT_COMPLETE_THROUGH_CURSOR` означает полноту распознанного текста до
конкретной строки. Это не обещание полной трассы провайдера или будущих сообщений.
Непроверенные тела инструментов находятся в отдельной очереди. Вложения пока
не копируются: доступный сопутствующий текст сохраняется, отсутствие файлов
отмечается явно. Промпт только с вложением тоже считается отправкой.
Неизвестная схема, повреждённая строка, чрезмерно большая запись и неполный
живой хвост остаются видимыми пробелами, последующий корректный текст сохраняется.

4 октября 2026 устранена несовместимость с наблюдёнными вариантами native
metadata: необязательное поле `user_input_order`, `fallback_token_limit_override`,
`mcp_attribution.error_reason`, ссылки `retained_source`, список `guardian_sources`
и флаг порядка источников. Значения проходят ограниченную структурную проверку
и не попадают в текстовую проекцию. Известные скрытые роли и reasoning исключаются
до проверки пользовательских метаданных; новые неизвестные поля по-прежнему
видны как пробелы. В смешанном сообщении берётся только текстовый блок; содержимое
вложения не переносится и отдельно отмечается.

Начиная с ремонта 12 сентября 2026 UTC распознаётся наблюдённый формат
автоматического запуска `codex_app.automation_update`: `function_call_output`
с `id` вида `fco_…`, без `call_id`, и строгим `<heartbeat>` из трёх полей
`automation_id`, `current_time_iso`, `instructions`. Метаданные получают
`origin: AUTOMATION`; такие повторы задания не увеличивают число человеческих
промптов. Они считаются отдельно как `automation_triggers` и перечислены
в `turns.json`. Отсутствующая связь вызова остаётся явно неприменимой —
`call_id` не восстанавливается догадкой. Тело, как у других инструментов,
сохраняется только после проверки точных байтов и регистрации SHA-256.
Произвольные результаты без `call_id`, другие поля/структуры, вложенный XML,
DTD и узнаваемое скрытое содержимое продолжают отклоняться.

Статус разделяет состояние процесса и полноту. `service_healthy` означает,
что launchd-служба загружена, отчёт свежий и сборщик сообщает `RUNNING`.
`coverage_healthy` означает отсутствие обнаруженных неразобранных пробелов;
`healthy` требует оба условия. `coverage_summary` и `attention` показывают
неразобранные пробелы даже у работающей службы. Обычная очередь инструментов,
ожидающих проверки, видна отдельно и сама по себе не считается сбоем.
`coverage: GAPS` остаётся общим показателем сессии. При определённо
инструментальной неизвестной схеме `text_coverage` может быть полным,
а `tools_coverage` — `UNSUPPORTED_SCHEMA`. Неопределённые и старые
неразмеченные пробелы консервативно относятся к `text_or_unknown`.
Команды `collector.py status` и `collector_service.py status` возвращают
ненулевой код при неразобранных пробелах, сохраняя отдельный признак
работоспособности службы в JSON.

Скрытые рассуждения, system/developer envelopes, дубли UI и закрытые внутренние
события исключены. Консервативные проверки узнаваемых credentials сохраняют
только очищенную проекцию с явным исключением; она не называется оригиналом.
Этот фильтр не доказывает отсутствия всех возможных секретов. Проверка каждого
tool body перед переносом остаётся обязательной.

## Устройство и восстановление

Единственный канонический журнал — append-only `research/archive`:
события плюс объекты по SHA-256. Существующие originals не переписываются.
`collector.version` сохраняет точные версии кода/конфига; отдельные новые события
фиксируют повторную интерпретацию после изменения адаптера. Coverage связывает
версию, сессию, предыдущий участок и новые свидетельства причинными ссылками.
Хеши проверяют внутреннюю согласованность, а не независимое нотариальное заверение.

Курсор восстанавливается из подтверждённых `collector.coverage`. Runtime cache
можно пересоздать. До продолжения чтения сверяется SHA-256 старого префикса.
Обрезание или изменение сохранённого источника вызывает ошибку; старые данные
остаются. После неопределённого сбоя частично записанный batch переиспользуется
по стабильным ключам, а курсор не продвигается раньше подтверждённой записи.
Один writer держит flock и выполняет полную проверку один раз на изменившийся
проход; отдельные источники не запускают повторные полные аудиты внутри прохода.

`capture_codex.py` совместим со сборщиком: уже сохранённый точный оригинал
переиспользуется после проверки. `capture.run_binding` связывает его с новым
исследовательским run, сохраняя исходные автора, ID и run. Стадии и checkpoint
проверяют эту связь. Автоматический журнал не заменяет проверку материалов и
охвата перед зависимым исследовательским шагом.

## Команды

Из корня лаборатории:

```sh
python3 -B scripts/collector_service.py status
python3 -B scripts/collector.py status
python3 -B scripts/chat_inventory.py
python3 -B scripts/collector.py verify
```

`chat_inventory.py` пересобирает новые подробные представления. Для ручного
полного переосмысления после изменения кода: остановить службу, выполнить
`python3 -B scripts/collector.py reconcile`, запустить службу и проверить status.
При конфликте с занятым collector lock команда завершается явно; повторить
после освобождения, не удалять lock-файл или оригинальные события.

```sh
python3 -B scripts/collector_service.py stop
python3 -B scripts/collector_service.py start
```

Stop действует до следующего ручного старта или входа пользователя в macOS:
установленный login plist остаётся. После изменения кода/настроек нужен
stop/start. Переустановка: сначала `prepare`, проверка полученного plist,
затем `install`. Отличающаяся существующая конфигурация не перезаписывается.
В рабочем экземпляре используется `/opt/homebrew/bin/python3`, собственный label
`org.philosophylab.collector`; глобальные настройки Codex/notify не меняются.

После прочтения конкретного безопасного tool body зарегистрировать точный hash:

```sh
python3 -B scripts/collector_review_tools.py --session SESSION_ID --line LINE --sha256 EXACT_SHA256
```

Нельзя одобрять весь диапазон по одному имени инструмента. Решение и manifest
версионируются; следующий проход добирает только совпавшие разрешённые байты.
Секреты и заблокированные внутренние тела не становятся допустимыми по hash.

## Работа в фоне и размер

Базовая пауза — 10 секунд; на дорогом проходе увеличивается до четырёх его
длительностей (максимум час), чтобы не занимать ядро постоянной проверкой.
Status показывает фактическую следующую паузу. При сне/выключенном компьютере
сбора нет; после входа/пробуждения служба добирает доступное продолжение.
Её работа проверена отдельно от Codex-процесса. Закрытие самого приложения
в живом пользовательском сеансе не тестировалось принудительно.

На неизменившихся файлах нет повторного переноса сообщений и пересборки всех
диалогов. Полный аудит выполняется при изменившемся batch, внешней записи и
периодически. Архив не помещается в контекст AI, но Python использует RAM
для индекса и проверок. Поэтому обещания нулевого роста памяти нет.

Синтетический тест 50 000 небольших событий: 18 batches по 10 — 7,006 с всего
в одном writer; последующие 17 batches после первого аудита — 0,277 с;
неизменившийся проход — 0,000890 с; полная проверка — 5,631 с.
Архив — 61,27 MB; пик RSS около 454 MiB после сбора и 748 MiB при дополнительной
полной проверке с загруженным индексом. Это не прогноз двух месяцев работы.
На 50 000 событий status просит пересмотреть масштаб/память. Крупные вложения
и число событий влияют больше, чем число отображаемых чатов.
Операционный лог ограничен двумя файлами примерно по 256 KiB; каноническая
история не ротируется. Системные stdout/stderr launchd обычно пусты, отдельно
учитываются при проверке диска. Сбой, устаревший heartbeat и пропуски видны
через status. После просьбы пользователя «пиши если будут траблы» 8 сентября
2026 UTC добавлена отдельная ежедневная проверка в Codex в 09:00 местного
времени (automation `philosophy-lab`). Она читает компактное состояние и сообщает
о новых проблемах/восстановлении; при нормальной работе молчит. Эта проверка
использует AI-запуск и расходует некоторое количество лимита. Сам сборщик
по-прежнему работает обычным Python-процессом без моделей. Оповещение не
мгновенное и зависит от доступности запланированного запуска Codex.

## Изображения в результатах инструментов

12 сентября 2026 UTC проверена наблюдённая форма `custom_tool_call_output`:
список текстовых блоков и `input_image` с локально переданными base64-байтами
PNG/JPEG/WebP и известным `detail`. Она учитывается как ожидающая отдельного
review запись инструмента, с числом изображений и явным
`SEPARATE_MEDIA_REVIEW_REQUIRED`. Подписи, URL и байты изображений в эту
проекцию не попадают. Это распознавание формы, не подтверждение содержимого
картинки или разрешение сохранить полный смешанный native record.

`capture_codex.py` по-прежнему отвергает такой полный оригинал даже после
обычного review tool body. Нужные безопасные картинки следует сохранять
отдельными явно выбранными артефактами; например, страницы прочитанных
источников уже входят в source snapshots эссе. Неизвестные поля, типы, URL
и значения `detail` остаются явными schema gaps. Нулевое число schema gaps
не означает, что очередь инструментов или вложений полностью захвачена.

## GitHub, резервные копии и будущие улучшения

Код, тесты, схемы и эта документация пригодны для будущего репозитория.
Runtime, фактический конфиг с частными ID/путями, логи и представления исключены
из обычного Git добавления. Публикация не включена. Позднее выбираются точные
экспорты для судей/визуализации; полный частный архив сохраняется отдельно.
Переносимый пакет и проверка импорта описаны в [ARCHIVE_FORMAT](ARCHIVE_FORMAT.md).
Локальный архив сам по себе не является резервной копией на другом диске.

Оставшиеся развития: отдельное копирование безопасных вложений/версий рабочих
артефактов, более удобный просмотр очереди инструментов, локальные сигналы
о сбое без AI-проверок, индекс для значительно больших историй, поддержка будущих native-схем.
Они не должны подменять текущую явно указанную полноту.

### October 31 display recovery and bounded cursor compatibility

A previously accepted visible record can have metadata that the current renderer
cannot validate. Such a record now creates an explicit `view_gap`; its body is
not rendered, the immutable original remains available, and other sessions keep
rendering. Display gaps are separate from the original capture coverage.

The optional `collector/capture-compatibility.json` enables only the reviewed
October 31 renderer/bookkeeping transition. The collector verifies the exact
stored predecessor source objects and signature, requires unchanged capture
code/configuration bytes apart from the two declared files, and binds the exact
current collector and renderer hashes. It appends one compatibility record and
a new version record. It never rewrites an old cursor or raw event. Unchanged
sources retain their previous proven cursor; a changed source still requires
prefix verification before its new tail is read. Changed review manifests,
explicit reconciliation, or any incompatible code/configuration retain the
normal strict reset behavior. A malformed compatibility declaration fails.
