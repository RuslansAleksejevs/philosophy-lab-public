# Приёмка отзывов: ограниченное сохранение видимого текста

Этот адаптер не запускает модели и не меняет рукописи. `--check-only` лишь читает назначенные файлы и одну сессию по её точному ID. Обычный запуск открывает один `Archive.writer()` на весь пакет; записи каждого отзыва принимаются до зависимого сравнения.

Сначала заново проверяются замороженный runner, очередь, схема, prompt, настройки запуска, все файлы результата и их hashes. `runner.inspect_native` повторно проверяет ID сессии, точный prompt (с разрешённым runner удалением конечных пробельных знаков), модель, effort, отсутствие чужого пользовательского текста/инструментов и видимый итог. Полученный JSON снова проходит те же правила приёмки. У каждой оценки остаётся точная версия и назначенная запись `assigned_entry` в истории эссе.

Для каждой известной видимой записи применяется `scripts/capture_codex.py`, если он принимает её исходную оболочку. Сохраняются её исходные байты и отдельный результат стандартного захвата. Проверяются ровно одна выбранная запись и её исходный hash.

Если стандартный адаптер не принимает оболочку, разрешён ограниченный запасной способ. Из фактической JSONL-строки извлекаются **точные JSON-string tokens** по пути `payload.content[i].text`, включая исходные кавычки и escapes. Токены не создаются повторной сериализацией. Их декодированный текст должен совпадать с уже проверенной видимой записью. Принимаются только известные сообщения `user` либо `assistant` с фазой `commentary`, `final` или `final_answer`, и блоки с `type` и `text` известного текстового типа. Дополнительные известные поля `annotations` и `logprobs` могут присутствовать; их значения не исследуются и не копируются. Поле `internal_chat_message_metadata_passthrough` также не исследуется и не копируется. Скрытая фаза, неизвестный тип содержимого, неизвестные ключи блока, неоднозначный JSON или несовпадение текста останавливают приёмку.

В запасном способе сохраняются сами токены, hashes исходной строки, номер строки, роль, фаза и причина несовместимости стандартного адаптера. Полная неподдержанная оболочка, чужие поля, скрытые рассуждения и внутренние данные не копируются. Событие имеет статус `EXACT_VISIBLE_JSON_STRING_FRAGMENTS`, а не `BOUNDED_COMPLETE`. Этот способ не доказывает полноту провайдерского журнала или подлинность серверной модели. Root отдельно сохраняет точные назначенные строки текущего человеческого разрешения; при несовместимой оболочке может использовать тот же ограниченный способ. Запасной способ не превращает задание модели в человеческое сообщение и не создаёт поддельный `capture.raw_record`.

Для подготовки до входа в writer экспортируется `freeze_visible_fragments(session_id, expected_cwd, selections, destination)`. Каждый элемент `selections` содержит точные `line`, `record_sha256`, `role`, `text` и, для assistant, `phase`. Hash исходной строки обязателен. Helper открывает только указанную сессию, сверяет ID/cwd и текст, сохраняет токены и `manifest.json` в `destination` внутри проекта. Он не открывает канонический архив и не запускает модель. Возвращённый manifest root может связать отдельным событием ограниченного захвата. Незавершённый хвост вне выбранных полных строк отмечается отдельно и не выдаётся за сохранённый.

Общий `CAPTURE_RECEIPT.json` имеет статус `BOUNDED_VISIBLE_CAPTURE_ACCEPTED` и явно указывает, все ли строки приняты стандартным адаптером. При невозможности безопасно принять текст сохраняются `ARCHIVE_GAP_ROOT_REPAIR_REQUIRED` и STOP; готового `ARCHIVE_RECEIPT.json` для этого отзыва не возникает. Частичные канонические события и прежние файлы сохраняются. Повторное применение разрешает лишь побайтово совпадающие записи; модель при этом не вызывается.

Проверенный законченный отзыв получает `REVIEW_ARCHIVED` и запись `evaluation`. Законченная попытка, отклонённая runner по формату/повтору, сохраняется как `QUARANTINED_REVIEW_ARCHIVED_MISSING`, без философского вердикта и без оценки в сводке. Неоконченные и аварийные попытки требуют отдельного решения root; этот скрипт не придумывает отсутствующие доказательства.

Для будущей пары требуются: `phase: pair`, два разных `pair_candidates` (исходные ID), `ordered_blind_ids` в точном порядке показа, `expected_output.pair_id`, а также замороженные `rubric_file` и `rubric_sha256`. JSON пары должен содержать `read_complete: true`, `verdict` и непустой `reason_ru`. При отсутствии этих полей выдаётся `PAIR_ARCHIVE_EXTENSION_REQUIRED`; порядок и победитель не угадываются. История пары ссылается на обе точные версии и оба `assigned_entry`.

Пример после принятия входов и завершения отзывов:

```sh
python3 -B runs/final-selection-20261018/archive_reviews.py --check-only --batch individual-001 --ids M01-N1 M01-N2
python3 -B runs/final-selection-20261018/archive_reviews.py --batch individual-001 --ids M01-N1 M01-N2
```

`--queue` меняет очередь; `--input-receipt` указывает её отдельно принятую квитанцию. Код адаптера, этот метод и synthetic tests должны быть заранее включены в квитанцию входов. Подтверждение пакета находится в `archive-batches/<batch>.receipt.json`, подтверждения отзывов — в `results/<job-id>/ARCHIVE_RECEIPT.json`.
